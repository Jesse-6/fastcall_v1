This quick guide presents key differences when using the new fastcall_v2 include file, which is made to support position independent binaries. Syntax and usage are almost the same as v1 (which is for fixed address binaries). The main differences are:

 - v1 already generate the final executables, so no external linking step (with 'ld' for example) is needed: the macro also do the linking itself;
 - v2 generate object file (.o) only, which isn't the final binary, and a linking step should be done to get the binary;
 - by only compiling only strictly needed sections/segments at the generated file, fastcall_v1 will always output smaller binaries than fastcall_v2, unless one really messes up too much with alignment within its source code. One must keep that in mind when chosing what type of binary is wanted, and if the tradeoff 'size vs address abstraction' worths that choice;
 - align macro on v1 aligns things on code in a static manner, so, all addresses are fully predictable in code, and no limitations exists on the normal usage of align statement;
 - align on v2 is similar, but the PIE nature of the resulting binary leads to limitation on how much one can really align things under a specific section: the section alignment is the limit, because anything above the value passed at section creation will not be predictable with relation to resulting dynamic address. The default in-macro alignment for all sections is 64 for data, and 16 for code section, covering most needs, but it can be overriden by the same method as v1;
 - '_code rwx' for read/write/execute code section is not working yet, and so far results in error if one tries to use it. A solution is still pending to be found;
 - in v1 context, one might need to recurse one extra reference for external data (like stdin, stdout or stderr), because they're only pointers to the data address, not the real data at startup;
 - in v2, when using the plain names, one get exactly that data (the *stream for stdout, for example). But, when referencing the name from GOT (e.g., 'GOT.stderr'), the same rule as of v1 apply;
 - in v1, external symbols has 'proto' namespace for direct call, and '__imp' namespace for indirect;
 - in v2, there isn't no namespace, but external symbols are always related to PLT and/or GOT, so, one might need to prefix a reference with PLT.symbol or GOT.symbol to address it properly. Examples cover both in detail;
 - include line for either dynamic or static address might be "include 'fastcall.inc'". This stub header detects the needed header based on format type;
 - 'format ELF64 executable 3' generates a static address executable code, thus using fastcall_v1;
 - 'format ELF64' generate code that can be position independent, thus using fastcall_v2. Link it with '-pie' to accomplish it. '-shared' for shared library (when using 'ld' as linker) already appears to result in address agnostic code being generated.

 By knowing that, one might be fully able to write code to either of those executable modes. And know that the resulting source will look quite the same, in practice.

For usage, examples will cover a better understanding than this quick guide could ever do, by being a quick guide. 'dynamic' folder has PIE binary examples, and 'static' folder has them as static address binaries.
